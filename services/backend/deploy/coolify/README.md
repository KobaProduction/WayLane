# WayLane / Coolify deployment plan

STATUS: SOURCE PACKAGING ONLY. This is a proposal, NOT a deployable Compose
manifest and NOT an authorization to change either Coolify instance.
The full runtime/ENV, ingress and secret contracts need explicit owner approval
before creating/changing managed Coolify resources.

## Real control planes

- Intens: https://coolify.intens.cloud (live vpn-core/web-app/data must not change).
- Koba Nexus: https://coolify.koba-nexus.ru (independent apps and servers).
- Each control plane has an existing SigNoz connection; live OTLP delivery
  for WayLane is not yet verified. Current Intens Alloy example exports HOST
  METRICS to VictoriaMetrics, not WayLane application logs.

## Dev and prod topology

Use THREE separate durable service boundaries: WayLane backend FastAPI :8000,
WayLane frontend Nginx :8080 and PostgreSQL with independent persistent
storage/backup. The initial backend runtime role is the existing all-in-one
with one worker (no new NATS); splitting node and scheduler processes later
requires a separate, approved NATS topology and leadership test.

DEV: Connect the Coolify Compose resource to the single Git-backed
`intens-cloud/infrastructure` deployment definition. Both `backend` and
`frontend` are built from the **same** `KobaProduction/waylane` commit,
with remote Git build contexts `services/backend` and `services/frontend`.
No direct source is taken from any former split GitHub repository.
For independently managed Coolify Applications, point both to the same
`KobaProduction/waylane` Git repository with component-specific paths.
Branch: main, backend Base Directory /services/backend, frontend Base Directory /services/frontend, respective Dockerfiles /Dockerfile.
Watch Paths services/backend/** for backend and services/frontend/** for frontend (plus explicit shared/contracts/** if consumed).
Enable automatic deploy on the configured branch only. GitHub App integration
owns its signed webhook; do NOT duplicate manual webhooks when that source
integration is used. If using public Git or deploy key instead, copy the
signed GitHub Push webhook URL generated by EACH Coolify application and
copy the secret from Webhooks > Manual Git Webhooks. Do not guess endpoints.
Keep push delivery proof separately for each of the two Coolify domains.

PROD: Use immutable published release images in GHCR:
ghcr.io/kobaproduction/waylane-backend:backend-vVERSION or sha-LONG_SHA
ghcr.io/kobaproduction/waylane-frontend:frontend-vVERSION or sha-LONG_SHA
Promotion should pin verified image digests, never floating latest; it must
not clone and build from main. Monorepo component-tag release workflows publish images
on GitHub Release published events. These are separate **image names**, not Git repositories. Private image pulls require a
protected read:packages principal, independent from Git cloning credentials.

## Public URLs and possible networking modes

The frontend is immutable and builds with VITE_BASE_API=/ by default.
Recommended: one public UI domain with a same-origin ingress forwarding
/api to the private backend and / to the frontend. OpenFlare, if chosen,
owns HTTPS/path routing, not Dockerfile builds.
Alternate: separate public UI and API domains, with an environment-built
VITE_BASE_API and explicit ALLOWED_ORIGINS. This cannot reuse a single
environment-agnostic immutable frontend image.
Alternate: reverse proxy to backend container DNS across a verified shared
Coolify Docker network. Picking a Coolify Destination does NOT automatically
attach two independent Compose applications to the same network.

No WayLane domain names, DNS, wildcard TLS, generated FQDN or proxy paths
were supplied. Do not invent any. After approval use actual Coolify domain
generation, then verify persisted FQDN, TLS and browser authentication.

## OTLP: reference and missing implementation

Doctor Dental uses OTLP/HTTP receiver port 4318, a Collector with batch
processor, and an authenticated OTLP/HTTP exporter to SigNoz. Adapt
this without reusing that project's credentials or tenant identity.
- Backend Python: OpenTelemetry instrumentation of runtime FastAPI,
  SQLAlchemy and outbound HTTP; structured stdlib logs correlated with
  trace_id/span_id, with credentials and payloads scrubbed.
- Frontend static Nginx writes structured access/error logs to stdout.
  Plain stdout IS NOT OTLP. It needs an approved collector transport:
  a filelog receiver using a shared, scoped volume, or a host-level
  collector with reviewed Docker log privileges. Avoid casually mounting
  docker.sock; never ship OTLP secret into browser/static assets.
- Separate PostgreSQL: its logs need a separately approved collector
  source; do not treat application logging as database logging.
- Collector: internal-only listener, batching/retry, protected bearer
  on outbound OTLP, explicit service.name/namespace/environment tags.

OTLP packages, collector runtime, shared variables and ingress have NOT
been configured yet, pending the variable/security contract. Test a
synthetic startup/access/error/trace in both SigNoz instances rather
than assuming container health proves telemetry delivery.

## Acceptance/rollback

1. Source checks and separate Dockerfile image builds pass.
2. New DEV Coolify resources on the approved server build from Git,
   with correct persisted branch, Watch Paths, ports and variables.
3. A push reaches both Coolify domains, creating independent successful
   deployments. Isolate development databases between the two sites.
4. Browser authentication, /api calls and /health work through real
   ingress and generated domains.
5. Logs/traces are searchable in the chosen SigNoz, with correct labels.
6. GitHub Release produces two GHCR images, which production can pull
   by immutable digest and roll back without a fresh source build.
7. Back up production database and verify forward-migration/rollback
   compatibility before any production traffic cutover.

Preserve the current Intens services, DNS, databases and production
webhooks as rollback until full acceptance and explicit authorization.
